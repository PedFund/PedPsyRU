# 01д.4 — сохранение и восстановление черновика

Дата: 2026-10-03. Только локальные вымышленные данные. Завершение/сохраненный результат — отдельный 01е, не реализован этим шагом. Форма, исправленный ключ TKI и вычислительная логика не менялись.

## Реализованный контракт

`GET /api/participant/attempts/:id/draft` возвращает `{attempt}`: собственные ответы, слайд, revision, status, закрепленные версии и отображаемую форму. `demo=true`, `persistence=true`; нет ключа, source_text, секретов, digest ответов или результата. Отдельный старый GET попытки остается совместимым.

`PUT` того же маршрута принимает строго три поля:

```json
{
  "expected_revision": 1,
  "current_item_id": "q08",
  "responses": [{"item_id": "q01", "value": "B"}]
}
```

Полный текущий снимок, не merge. Максимум 30 уникальных пар закрепленного выпуска, только канонические A/B; пропуск — отсутствие строки. Revision — безопасное целое, >=0, меньше MAX_SAFE_INTEGER. Неизвестные/лишние поля, ID, кириллические А/Б, дубли и неверный слайд отвергаются. Лимит JSON — 8192 байта. Версии, роль и область клиент не назначает.

На каждом запросе проверяются participant-сессия, срок/отзыв/версия, текущие участник/исследование, enrollment, назначение, группа и этап. Staff-токены обеих ролей не разрешают писать, даже после переименования cookie. PUT требует точный Origin и session-bound X-CSRF-Token. Чужой/недоступный ID — одинаковый 404, без сессии — 401, неверный ввод — 400, stale revision — 409 REVISION_CONFLICT, completed — 409 ATTEMPT_COMPLETED. Закрытый origin/CSRF — 403; метод — 405; объем — 413; не JSON — 415. Ошибки не эхо тела запроса.

`storage/drafts.js`: BEGIN IMMEDIATE → повторная проверка доступности → валидация/revision → замена ответов + CAS позиции/revision+1 → обязательный метаданный аудит → commit. Сбой записи или аудита откатывает весь снимок. SQLite допускает одного писателя; [границы транзакций](https://www.sqlite.org/lang_transaction.html) не заменяют проверку прав. CSRF/Origin учитывают [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Очистка — тот же PUT с пустыми responses и первым item после подтверждения, только собственный draft. T1/T2 не получают ответы T0. Completed можно читать как неизменяемый первичный протокол, нельзя изменять/очищать. Нет создания новых попыток, нового выпуска, расчета, завершения или записи attempt_results. Новая миграция не нужна; 001/002/003 неизменны.

## Браузер и восстановление

`/access` → свое назначение → `/take?attempt=UUID`. Каждая пара на отдельном слайде. Тексты и порядок — из закрепленного выпуска, не текущего файла формы. `/` остается отдельной несохраняемой демонстрацией; `/api/score` не менялся и в сохраненном прохождении не вызывается.

Очередь `web/draft-model.js` последовательно пишет снимки и объединяет быстрые ожидающие изменения. Подтверждение старого запроса не объявляет более свежий выбор сохраненным. UI показывает сохранение/подтвержденную revision/конфликт/ошибку. Таймаут 10 секунд, потерянный ответ и конфликт блокируют новые записи: сначала явная загрузка сервера с предупреждением о замене локального неподтвержденного выбора. Автоматического retry/merge нет. Успешный ответ теряется — запись могла состояться; повтор со старой revision получает конфликт, GET уточняет фактическое состояние. Это не семантическая идемпотентность.

Восстанавливаются только подтвержденные сервером ответы и слайд. Нет скрытого сохранения диагностических данных в localStorage/cookies и записи при закрытии через beacon. Предупреждение beforeunload при dirty — не гарантия доставки. На последнем слайде проверяется полнота, но 30 ответов остаются draft: результат пока не создается.

## Проверки и подтвержденная готовность

`npm run test:draft`: **22/22**; `npm test`: **119/119** = 22 новых + 97 прежних.

- 15 service/HTTP тестов: свой snapshot/версии; частичный/полный ввод; конкурентные запросы с одной revision (200/409); invalid/extra/duplicate; чужие ID; staff realm; Origin/CSRF/лимиты; отзыв/закрытие/исключение/expiry; очистка/T1/T2; rollback SQL и mandatory audit; метаданный аудит; повторное открытие файла/новый вход; completed; потерянный ответ API. SQL completed в тесте — fixture, не публичный сервис.
- 7 тестов очереди: копия состояния; coalescing; новый выбор во время запроса; conflict/явная загрузка; network/auth/completed без auto-retry; неверный ack/загрузка при запросе; readonly/очистка.
- Реальный браузер, отдельная временная in-memory база: выбор и переход к q08 → подтверждение → reload вернул ответы/q08; две вкладки со stale revision → видимый конфликт/блокировка, подтверждаемая загрузка вернула победивший A; logout → новый login → тот же attempt_id, q08, 4/30, revision=8. Ровно одна видимая пара. Скриншот вне Git.
- Основной учебный файл не получает тестовых credentials/ответов; integrity/FK проверяются отдельно. Не добавлено миграций, не переписан core. База, секреты и скриншот не публикуются.

Готовность: учебный черновик/восстановление подтверждены указанными тестами, не production и не доказанная научная валидность методики. Полная межбраузерная/мобильная/offline матрица, аудит доступности и независимый security audit не выполнены. Реальный набор, согласия, HTTPS/Secure/MFA, резервное копирование, manager CRUD и редактор методик не включены.

Следующий предлагаемый блок **01е**: серверное завершение только сохраненного полного снимка, существующий scoreTki с закрепленными версиями, атомарная фиксация одного результата и проверка повторов/гонок/сбоев. Автоматически не начат.
