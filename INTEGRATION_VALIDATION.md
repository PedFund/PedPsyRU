# 01е.3 — подготовка интеграции TKI-пилота в main

Дата: 2026-10-03. Репозиторий PedFund/PedPsyRU. Это отчет о проверенном кандидате, **не утверждение, что merge уже выполнен**. Публикация сайта, новые права и реальные данные этим шагом не включаются.

## Почему код оставался в ветках

Шаги 01а–01е публиковались зависимой цепочкой PR #1–#7; все они оставались open/unmerged. Последняя ветка содержит весь пилот, не семь отдельных программ. GitHub по умолчанию показывает main, где до интеграции были только AGENTS.md, ROADMAP.md и начальный README. Цепочку следовало раньше вывести на интеграционную приемку; создание следующего звена не является заменой интеграции.

AGENTS.md разрешает автономную техническую работу, но прямо требует отдельного разрешения владельца для merge в main. Предыдущее указание также запрещало автоматически объединять все открытые PR. На текущем запросе подготовка продолжена; разрешение на один итоговый merge запрошено отдельно, main пока не изменена.

Прямой REST-ответ PR после перенаправления: base SHA `1a424176...`, head `9743d9b9...`, mergeable=true, mergeable_state=clean. GitHub сформировал предварительный merge commit `25c13479680585d8088868f072bba9f927dce6a9` с обоими ожидаемыми родителями; его tree **точно равен** `c9f8b008...` полного пилота. `npm test` вновь фактически запущен: **134/134**, 0 ошибок/пропусков. Локальные файлы совпадают с деревом предварительного объединения. Таким образом проверено содержимое будущего общего дерева, а не только изолированный набор изменений последнего шага. Это локальная техническая проверка, не независимый security/научный аудит. Детали функциональных проверок — COMPLETION_VALIDATION.md, DRAFT_VALIDATION.md и прежние отчеты.

В кандидате нет .local, SQLite, секретов, выгрузок или скриншотов. Обработка остается прежней; форма/ключ/миграции и инструкции не переписываются ради интеграции.

## Следующий разрешенный маршрут

1. После отдельного разрешения владельца заново проверить main/head, preview и обязательные проверки. При изменении исходных точек не объединять старый непроверенный кандидат.
2. Объединить **один PR #7** в main методом merge с ожидаемым head SHA. Не squash/rebase/force: сохранить историю коммитов прежних этапов и main. Семь PR по отдельности не объединять.
3. Проверить фактический новый main: полный набор файлов/инструкции, отсутствие запрещенных артефактов, происхождение прежних head-коммитов; повторить тесты на точно совпадающих файлах.
4. Старые #1–#6 рассматривать как уже включенные только после проверки происхождения и фактического дерева. Их обсуждения и ветки не удалять; если PR остались open, зафиксировать superseded by #7 и закрывать как замененные, не выполнять дополнительные merge.
5. Обновить STATUS/BACKLOG фактом интеграции только после успеха. Следующие функциональные ветки начинать от актуальной main, не снова от цепочки.

Пока шаг 1 ожидает разрешения; интеграция в main не объявляется выполненной. Производственная архитектура/развертывание — отдельные фазы и решения, не следствие merge.
