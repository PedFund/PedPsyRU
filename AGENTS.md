# AGENTS.md — правила работы с МетодТест

Это действующая краткая инструкция для coding agents. История фаз и прежние поручения сохранены в Git, но не являются текущими командами. Перед работой прочитайте [CURRENT_STATE.md](CURRENT_STATE.md); для задач о методиках сначала откройте [methods/README.md](methods/README.md).

## Приоритет источников

1. Конкретное текущее поручение владельца.
2. Ограничения безопасности, сохранности данных и научной корректности.
3. [CURRENT_STATE.md](CURRENT_STATE.md) — фактическая контрольная точка.
4. [methods/README.md](methods/README.md) — навигация по библиотеке.
5. [ARCHITECTURE.md](ARCHITECTURE.md), профильные документы и код задачи.

## Режим работы

- Одно поручение — один ограниченный результат. Не переходите самостоятельно к новой функции или фазе.
- До изменений проверьте ветку, HEAD, `git status --short`, индексированные и новые файлы. Локальная работа принадлежит владельцу: не отменяйте и не перезаписывайте ее.
- Не проводите общий аудит и не перечитывайте всю историю без необходимости.
- Сначала адресные проверки, затем требуемая регрессия. Не повторяйте полный набор без анализа причины отказа.
- Не выполняйте длительный опрос GitHub Actions. После публикации сообщите SHA и ссылку на CI и завершите работу, если диагностика результата не поручена.
- Не объявляйте успех по старому SHA или частичному CI. Merge, развертывание, обновление стенда и следующая задача требуют отдельного разрешения.
- Запрещены `git reset --hard`, `git clean`, force push и иные действия с риском потери работы без явного согласования.

## Доступ и данные

- Сохраняйте роли и серверные проверки. Новое право требует решения владельца. Не обходите MFA и не меняйте пароли, recovery-данные, ключи, токены или секреты.
- Не ослабляйте RLS, CAS, аудит, проверки владельца/области, CSRF/Origin/Host, версионирование и неизменяемость закрепленных данных.
- UI не является границей доступа. Изменения идут через сервер; impersonation запрещен, ответы и согласия вводит участник.
- В тестах только синтетические данные. Реальные ФИО, email, ответы и результаты запрещены в коде, фикстурах, логах и Git.
- Перед коммитом проверяйте diff, новые файлы, секреты, базы, дампы и конфигурации; значения секретов не выводите.

## PostgreSQL и версии

- Не очищайте, не пересоздавайте и не мигрируйте рабочую PostgreSQL без разрешения. Интеграционные тесты — только в изолированных `pedpsy_ci_*`.
- Примененные миграции не переписываются; изменение схемы получает новую последовательную append-only миграцию.
- Исследования, группы, этапы, назначения, участники, анкеты, ответы, результаты и аудит задним числом не меняются. Новая версия не заменяет закрепленную старую.
- Обновление/восстановление требует проверенной копии и приемки `pg_dump`/`pg_restore`, но это не разрешение трогать рабочий стенд.
- Не добавляйте в Git PostgreSQL data-каталоги, дампы, `.local/` и локальные конфигурации.

## Методики

- Сначала используйте [methods/README.md](methods/README.md) и существующие манифесты; не восстанавливайте повторно сохраненные материалы.
- Архив, восстановленная форма, работающий обработчик, назначаемый выпуск и научно/правово утвержденная методика — разные статусы.
- Не заменяйте ключ похожей адаптацией и не меняйте порядок вопросов, ответы, шкалы, реверсы, формулы, нормы или интерпретации без методологической проверки.
- Не меняйте идентификаторы и digest выпусков. Новая версия добавляется отдельно. Синтетический пример не доказывает научную валидность или право публикации.
- Архивная запись не делает методику назначаемой. Архивный код не исполняется: обработчик подключается только явным allowlist/versioned runtime.
- Не удаляйте и не перемещайте исходники и манифесты без проверки ссылок и контрольных сумм.

## Git и приемка

- `main` — стабильная ветка; разработка идет отдельно, stacked PR явно указывает базу.
- Перед публикацией проверьте `origin`, diff, `git diff --check`, секреты и случайные файлы. Коммит содержит только текущее поручение.
- Обычный push допустим по задаче; force push, переписывание истории, создание/смена базы PR и merge — только по прямому поручению.
- После изменения head прежний зеленый CI не является приемкой.
- Сначала проверяйте синтаксис и адресные тесты; для SQL/HTTP/доступа — изолированную PostgreSQL и негативные границы.
- Перед merge обязательна итоговая приемка точного head: локальная регрессия, PostgreSQL, браузерные E2E, зависимости, секреты и все required jobs.
- Не пропускайте тесты, не уменьшайте браузерные повторы, не ослабляйте assertions и не увеличивайте timeout вместо установления причины.
- В отчете разделяйте local, PostgreSQL, browser и GitHub CI. Ошибки, отмены и skipped не являются успехом.

Если решение требует новой архитектуры, научного выбора, изменения реальных данных, оплаты или инфраструктуры — остановитесь и укажите конкретный блокер.

## Завершение задачи и подготовка Merge в main

- Цель функциональной задачи — не только commit/push/PR, но и подтвержденная готовность изменений к интеграции в актуальную `main`. Не считайте публикацию PR завершенной интеграцией.
- После адресных проверок опубликуйте коммит и сообщите SHA, PR и ссылку на CI. Не тратьте агентную сессию на длительное ожидание GitHub Actions. Если результат CI еще неизвестен, явно обозначьте ожидание и завершите текущую сессию.
- При ошибке CI определите первый содержательный отказ и предложите минимальное адресное исправление. Не создавайте новый функциональный PR поверх неисправленного без явной необходимости; не ослабляйте обязательные тесты.
- Перед приемкой проверьте все незавершенные зависимые PR и различия с актуальной `main`. Подготовьте обоснованный порядок слияния либо одну консолидированную интеграционную ветку/PR после согласования смены базы или создания нового PR. Не создавайте новые уровни цепочки без необходимости.
- При интеграции проверяйте сохранение всех реализованных функций, форм, ключей, обработчиков, манифестов, миграций, научных ограничений и истории. Отдельно учитывайте пересекающиеся открытые PR, включая прежние функциональные изменения.
- Перед Merge проверьте полный обязательный CI на точном итоговом состоянии относительно актуальной `main`, отсутствие конфликтов и сохранность данных. Частичные, отмененные и старые запуски не являются приемкой.
- При успешной приемке явно сообщите владельцу: **«Готово к Merge в main»**; укажите целевой PR/ветку, SHA, результаты проверок, зависимости и оставшиеся риски. Если есть блокер, сообщите точную причину и следующий минимальный шаг.
- **Merge выполняйте только после отдельного явного разрешения владельца.** После него проверьте действительный SHA `main` и статус проверок. Затем предложите актуализацию `CURRENT_STATE.md` и закрытие избыточных PR, но не выполняйте их без согласования.
- Merge кода не является разрешением на развертывание, миграцию или обновление рабочей PostgreSQL, изменение ключей либо обработку реальных данных. Для каждого такого действия требуется отдельное разрешение.
## Контуры и завершение

- UI-only стенд не доказывает хранение. Учебный стенд, Selectel, внешняя почта, домен, реальные аккаунты и данные требуют отдельного поручения и приемки.
- О загрузке свыше 500 МБ заранее сообщите состав и объем.
- В финале укажите только проверенные ветку, SHA, файлы, проверки, ограничения и нужное решение владельца. После достижения результата остановитесь.
