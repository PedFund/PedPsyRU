## 1. Метод и границы

Подход: **измерение → диагностика → ограничения → оптимизация → повторное измерение → масштабируемость**.

Использованные источники:

| Источник | Что дал |
|---|---|
| `AGENTS.md`, `CURRENT_STATE.md`, `ARCHITECTURE.md`, `DATA_MODEL.md`, `README.md` | правила, контрольная точка, границы |
| исходный код `src/`, `storage/postgres/`, `storage/access.js` | фактические алгоритмы, лимиты, SQL, RLS |
| read-only SSH-диагностика ВМ Selectel | CPU/RAM/диск, Node.js, PostgreSQL, nginx, журналы, бэкапы |
| `/var/log/mettest/access.log` рабочего контура | реальные задержки и коды ответов |
| безопасные HTTP-запросы к рабочему сайту | доступность, заголовки, TLS, задержка |
| k6 2.4.0 на изолированном стенде | вход, регистрация, прохождение, конфликты, завершение |

Ограничения аудита:

- на рабочем контуре **не выполнялись** массовая регистрация, прохождение методик и запись тестовых данных;
- `pg_stat_statements` не установлен, поэтому на проде нет статистики по запросам; диагностика SQL выполнена на изолированной копии;
- серверный доступ был read-only: секреты не выводились, конфигурация не менялась, миграции и перезапуски не выполнялись;
- тестовый стенд отличается от прода (Windows, 16 потоков, пул 4, 1440 попыток в БД) — абсолютные значения не переносятся без оговорок.

### 2.3. Что происходит при сохранении одного ответа

`PUT .../draft` → `createParticipantApi.save` (`src/application/participant-api.ts`) → `PostgresParticipantGateway.session()` (`src/adapters/postgres/identity.ts`) → `PostgresUnitOfWork.run()` (`src/adapters/postgres/unit-of-work.ts`).

Фактически на **один** PUT выполняется:

1. `uow.context(token)` — отдельное соединение из пула, `BEGIN`, `assertRuntimeClient`, `set_config`, `session_actor()`, `COMMIT` (≈ `identity.ts:43-57`);
2. `withSession(token)` — **второе** соединение, `BEGIN`, `lock_participant_identity()`, `SELECT ... FROM pedpsy.attempts ORDER BY id`, `INSERT audit`, `touch_session`, `COMMIT` (`identity.ts:59-76`);
3. `uow.run(context, …)` — **третье** соединение, `BEGIN`, `assertRuntimeClient`, `ensure()` (ещё один `session_actor()`), `lock_participant_scope`, `SELECT` попытки, `SELECT` ответы, `UPDATE` попытки, `INSERT`/`DELETE` ответов, `INSERT` аудита, `touch_session`, `COMMIT` (`unit-of-work.ts:58-176`).

Итого: **3 транзакции, 3 получения соединения из пула, ≥3 проверки runtime-роли, 2–3 вызова `session_actor()`, ~15–20 SQL-операторов** на один клик «Далее». Пункт 2 содержит запрос без `WHERE` по всей таблице `attempts` — см. F-1.

### 2.5. RLS и права

`attempts` защищена политикой `attempt_read USING pedpsy.can_read_attempt(id)`; `can_read_attempt` вызывает `owns_active_attempt`, а тот — `session_actor()` и JOIN по enrollments/assignments/groups/stages (`002_access_rls.sql:52-88`). Функции `STABLE`, но зависят от `id` строки, поэтому PostgreSQL вычисляет их **для каждой строки**, а не один раз на запрос. `responses` использует ту же функцию по `attempt_id` (строк мало — цена приемлема).

## 5. Найденные проблемы

Классификация: **[П]** — подтверждено измерением/кодом; **[Г]** — гипотеза, требует проверки.

### F-1 [П] RLS-политика `attempts` вычисляется построчно, а `session()` читает все попытки базы

- **Файл/функция:** `src/adapters/postgres/identity.ts:70` (`SELECT id,status,revision,current_item_id FROM pedpsy.attempts ORDER BY id`), политика `attempt_read` в `storage/postgres/002_access_rls.sql:100`, функции `can_read_attempt`/`owns_active_attempt` (`002:78-88`).
- **Механизм:** запрос без `WHERE`; RLS вызывает `can_read_attempt(id)` для каждой строки; внутри — JOIN по enrollments/assignments/groups/stages и `session_actor()`. Стоимость линейна по числу попыток **во всей базе**, а не по числу попыток участника.
- **Условия:** любой запрос участника, т.к. `identity.session()` вызывается в `save`, `complete`, `result`, `read`, `form`, `retry` (`participant-api.ts:10-21`).
- **Измерение:** PostgreSQL-лог изолированного стенда: `duration: 725.131 ms` на 1440 попытках; прод: сохранение 230 мс при 245 попытках; оценка ~0.5–0.9 мс на попытку.
- **Влияние:** при 300 участниках × 6 попыток ≈ 1800 попыток → ~1 с на каждый запрос; при 1000 участниках — секунды, платформа перестаёт отвечать. Это **главный барьер масштабирования**.
- **Исправление:** передать в запрос `study_id`/`participant_id` и читать только свои попытки через `JOIN stage_enrollments` + индекс; либо заменить RLS-чтение на `SECURITY DEFINER` функцию `list_own_attempts()`; либо задавать `app.study_id`/`app.participant_id` в начале транзакции и строить политику по этим GUC с индексом.
- **Риск:** изменение политики RLS требует регрессии прав (негативные тесты «чужой участник/чужое исследование»), иначе можно открыть чужие попытки.

### F-2 [П] Три транзакции и три получения соединения на одно сохранение ответа

- **Файл/функция:** `src/application/participant-api.ts:11-13`, `identity.ts:67-76`, `unit-of-work.ts:43-57,58-176`.
- **Механизм:** `session()` отдельно создаёт контекст (`uow.context`), отдельно проверяет сессию (`withSession`) и только потом `save()` открывает третью транзакцию с повторной проверкой `session_actor()`.
- **Условия:** каждое сохранение, завершение, чтение результата, вход в форму.
- **Измерение:** 3 × `BEGIN/COMMIT` в логе PG на один PUT; 3 × `assertRuntimeClient`; на стенде при пуле 4 и 100 VU клиентское p50 сохранения 10.2 с (очередь на пуле), серверное p50 0.5 с (F-1).
- **Влияние:** втрое больше соединений и транзакций, чем нужно; при пуле 8 и 300 участниках — очередь и рост хвоста задержек.
- **Исправление:** объединить `context`+`withSession`+`run` в одну транзакцию с одним `session_actor()`; кэшировать контекст в рамках запроса; проверять runtime-роль один раз на соединение (при `connect`), а не на каждую транзакцию.
- **Риск:** объединение сокращает окно проверок; нужно сохранить порядок блокировок и повторную проверку прав под блокировкой.

### F-3 [П] scrypt: 134 МБ и ~0.4 с на операцию, жёсткая очередь; 200 входов дают 429

- **Файл/функция:** `storage/access.js:6-8` (`SCRYPT`), `src/adapters/derivation-gate.ts`, `src/bootstrap/login-policy.ts`.
- **Механизм:** `N=131072, r=8` → память 128·N·r ≈ 134 МБ, время ~0.4 с. `DerivationGate` в пилоте: 2 параллельно, очередь 512, таймаут 30 с. 200 одновременных входов × 0.4 с / 2 = 40 с > 30 с → часть запросов получает 429.
- **Условия:** одновременный вход/регистрация более ~150 человек, а также любой всплеск.
- **Измерение:** scrypt локально 385–403 мс, на проде вход 438 мс; нагрузочный тест 200 VU: **140 успешно, 60 × 429**, p95 30.3 с.
- **Влияние:** массовый вход части пользователей не проходит; повтор через 30 с создаёт вторую волну.
- **Исправление (без снижения стойкости):** поднять `derivationConcurrency` до 4 при 4 vCPU и проверить память (4×134 МБ + Node + PG ≈ 700 МБ — допустимо при 4 ГБ), увеличить таймаут очереди до 60 с, либо вынести scrypt в отдельный процесс/пул с собственным лимитом, чтобы HTTP-обработчики не ждали. Не уменьшать N/r/p.
- **Риск:** при 2 vCPU concurrency 4 не даст пропускной способности (4×0.4 с на 2 ядрах), только увеличит очередь; без вертикального масштабирования или отдельного воркера предел ~5 входов/с.

### F-4 [П] Жёсткий глобальный лимит receipt — 100 запросов / 5 минут

- **Файл/функция:** `storage/postgres/024_registration_receipt.sql:45-55` (`'global',300000,100`).
- **Механизм:** лимит зашит в SQL и не настраивается из окружения (в отличие от login/registration).
- **Условия:** более 100 подтверждений за 5 минут на весь стенд.
- **Измерение:** регистрация 200 → ровно **100** отказов `REGISTRATION_THROTTLED`, успех 77.6%, p95 30.2 с; 100 → 100% успех.
- **Влияние:** массовая регистрация 200+ человек в одном окне невозможна; это ограничение не вычислительное, а административное.
- **Исправление:** новая модель регистрации не должна синхронно зависеть от receipt (см. `REGISTRATION_REDESIGN.md`); для текущей модели — вынести лимит в конфигурацию с обоснованным значением и отдельным антиспам-контуром.
- **Риск:** простое повышение лимита усиливает спам-регистрацию и расход писем.

### F-5 [П] Лимит входа на email — 5 попыток / 15 минут, считая успешные входы

- **Файл/функция:** `087_pilot_login_admission.sql:50` (`'pedpsy-email-login:'…,900000,5`), `identity.ts`/`participant-registration.ts`.
- **Механизм:** bucket увеличивается на каждой попытке, включая успешные; 6-й вход за 15 минут — 429.
- **Условия:** перезагрузки страницы, повторный вход после сбоя, несколько устройств, серия тестов.
- **Измерение:** при нагрузочных прогонах приходилось очищать `pedpsy.login_throttles` между испытаниями; без очистки тестовые аккаунты получали 429.
- **Влияние:** добросовестный участник может быть заблокирован на 15 минут; для реального пилота это риск поддержки.
- **Исправление:** считать только неуспешные попытки (или успешный вход сбрасывать bucket), оставив строгий лимит на неудачи; для повторных запросов использовать идемпотентность.
- **Риск:** ослабление антиперебора; компенсировать per-IP/глобальным лимитом и задержкой.

### F-6 [П] Повторный вход отзывает предыдущую сессию (одна активная сессия на участника)

- **Файл/функция:** `storage/postgres/004_participant_identity.sql:39` (`UPDATE participant_sessions SET revoked_at_ms=at WHERE credential_id=c.id AND revoked_at_ms IS NULL`).
- **Механизм:** каждый успешный вход инвалидирует все прежние сессии участника.
- **Условия:** вход на втором устройстве/вкладке, повторный вход, автоматический re-login.
- **Измерение:** в сценарии конфликта второй вход сделал первую сессию недействительной; параллельные сохранения из неё получили 401.
- **Влияние:** нельзя продолжить тест на другом устройстве; при потере cookie и повторном входе старая вкладка «умирает»; в массовом сценарии это может выглядеть как случайные 401.
- **Исправление:** разрешить несколько сессий с лимитом (например, 3) и отзывать только самую старую; либо явно документировать односессионность и показывать пользователю понятное сообщение.
- **Риск:** больше активных токенов — больше поверхность атаки; нужен лимит и аудит.

### F-7 [П] `session()` возвращает все попытки участника без пагинации

- **Файл/функция:** `identity.ts:70-73`; DTO `participant-api.ts:7`.
- **Механизм:** список попыток отдаётся целиком в `/participant/session`; при 6 попытках это мало, но при повторных прохождениях и T0–T2 растёт.
- **Условия:** много попыток/повторных прохождений.
- **Измерение:** не измерялось отдельно; видно по стоимости F-1.
- **Влияние:** вторично по сравнению с F-1, но усугубляет сериализацию и трафик.
- **Исправление:** отдельный лёгкий эндпоинт «мои активные попытки» с `WHERE status='draft'` и лимитом.

### F-8 [П] `assertRuntimeClient` на каждую транзакцию

- **Файл/функция:** `unit-of-work.ts:21-28, 36, 48, 63`; `identity.ts:27`.
- **Механизм:** запрос к `pg_roles/pg_class/pg_namespace/pg_database/pg_auth_members` перед каждой транзакцией.
- **Измерение:** 0.48–9.1 мс на вызов в логе PG; 3–4 вызова на запрос.
- **Влияние:** 2–30 мс на запрос; на фоне F-1 мало, но при объединении транзакций станет заметным.
- **Исправление:** кэшировать результат на соединение (проверять при `connect`), инвалидировать при смене роли.

### F-9 [П] Отсутствие наблюдаемости SQL на проде

- **Файл/конфигурация:** PG (`pg_stat_statements` не установлен, `log_min_duration_statement=-1`, `log_lock_waits=off`).
- **Влияние:** нельзя доказать узкое место на проде, нельзя отследить регрессию; аудит вынужденно опирается на изолированную копию.
- **Исправление:** включить `pg_stat_statements` (shared_preload_libraries + рестарт) или как минимум `log_min_duration_statement=500ms`, `log_lock_waits=on`, `track_io_timing=on`; вывести p95/p99 из access-лога в мониторинг. Требует окна и разрешения.

### F-10 [П] Аудит пишется на каждую ошибку, включая анонимные

- **Файл/функция:** `participant-app.ts:76-82` → `extension.denied` → `registration_denials`/`record_participant_denial`.
- **Механизм:** любой 4xx (кроме 404) порождает запись в `access_audit_events`.
- **Измерение:** 9 392 записи `participants.registration.http_denied` после тестов; боты на `/cgi`, `/client/index.php` дают 403.
- **Влияние:** таблица аудита растёт от внешнего шума; при атаке — дополнительная запись на каждый запрос (усиление нагрузки).
- **Исправление:** семплирование/агрегация для анонимных отказов, либо отдельный счётчик; сохранить аудит значимых событий.

### F-11 [Г] Очередь перед обработчиком под нагрузкой

- **Наблюдение:** клиентское p50 сохранения 10.2 с при серверном p50 ~0.5 с (access-лог). Разрыв ~9.7 с не объясняется временем обработчика.
- **Гипотезы:** ожидание соединения пула (4 в demo), accept-очередь Node, событийный цикл, TCP.
- **Как проверить:** метрики `pool.waitingCount`, event-loop lag (`perf_hooks.monitorEventLoopDelay`), `ss -lnt` Recv-Q, `node --prof`.
- **Влияние:** даже при исправлении F-1 очередь может остаться; пул 8 на проде и 3 получения на запрос — риск.

### F-12 [Г] scrypt и память при увеличении concurrency

- **Механизм:** 134 МБ на операцию; при concurrency 4 — ~536 МБ, плюс Node (~90 МБ) и PG (`shared_buffers` 128 МБ, соединения). На 3.9 ГБ это допустимо, но без swap любой выброс приведёт к OOM-killer.
- **Как проверить:** замер RSS при 4 параллельных входах, `dmesg` на OOM.

### F-13 [П] Инфраструктурные пробелы

- off-site бэкапа нет; при потере ВМ данные и бэкапы потеряны;
- алерты только в journal, внешнего канала нет;
- HTTP/2 не включён, gzip включён глобально (для JSON это плюс, для TLS — не проблема);
- `worker_connections 768` при 2 воркерах = 1536 соединений — достаточно для 1000 пользователей, но без `limit_req` боты могут занимать соединения;
- нет `pgbouncer`; при горизонтальном масштабировании приложения пул на каждый инстанс умножается.

## 6. Что проверено и что нет

**Проверено:** доступность сайта, версия и её совпадение с `main` (код), архитектура маршрутов, реальные задержки из access-лога, заголовки/TLS, конфигурация ВМ/PG/nginx, отсутствие ошибок в journal, бэкапы/таймеры, стоимость scrypt, поведение 200 входов, регистрации 20–200, прохождения 100/300, конфликты записи, целостность данных после нагрузки, RLS-запрос `attempts` (725 мс при 1440 строках).

**Не проверено:** поведение на 1000 пользователей (нет среды), длительный soak на проде (запрещено), `pg_stat_statements` на проде (не установлен), точная причина разрыва клиент/сервер (F-11), влияние конкурентных регистраций на сохранение ответов при 300 VU в одном прогоне (попытка mixed прервана script-исключениями; после исправления защитных проверок сопоставимый прогон не повторялся — см. `PERFORMANCE_BASELINE.md`, 4.6a), стоимость `EXPLAIN (ANALYZE, BUFFERS)` для всех запросов (сняты только ключевые).

## 8. Приложение. Команды read-only диагностики (воспроизводимость)

Использованы только читающие команды; секреты не выводились, значения `PGPASSWORD`/`PEDPSY_MFA_KEY`/`PEDPSY_CONTACT_KEY`/SMTP не печатались.

```bash
# система и процесс
nproc; lscpu | grep -E 'Model name|CPU\(s\)|Thread|Core|Socket'
free -m; swapon --show; df -hT /; cat /proc/loadavg
systemctl show mettest -p MainPID -p User -p LimitNOFILE -p NRestarts
ps -o pid,rss,%cpu,nlwp,etime -p "$(systemctl show mettest -p MainPID --value)"
readlink -f /opt/mettest/app; node --version
ss -ltnp

# PostgreSQL (владелец схемы/администратор, только чтение)
sudo -u postgres psql -Atc "select version();"
sudo -u postgres psql -Atc "select name||'='||setting from pg_settings where name in ('max_connections','shared_buffers','work_mem','effective_cache_size','log_min_duration_statement','log_lock_waits','shared_preload_libraries');"
sudo -u postgres psql -Atc "select count(*),count(*) filter (where state='active') from pg_stat_activity;"
sudo -u postgres psql -Atc "select count(*) from pg_locks where not granted;"
sudo -u postgres psql -d "$DB" -Atc "select relname,pg_size_pretty(pg_total_relation_size(relid)) from pg_stat_user_tables order by 2 desc limit 10;"

# nginx и журналы
nginx -T | grep -E 'worker_processes|worker_connections|limit_req|client_max_body_size|proxy_'
journalctl -u mettest --since '-7 days' | grep -cE 'ERROR|Exception'
tail -n 200 /var/log/mettest/access.log

# бэкапы/таймеры
ls -lah /var/backups/mettest | tail
systemctl list-timers --no-pager
```

Если бы доступа не было, эти команды (и права `sudo -u postgres psql`, `systemctl status`, чтение `/var/log`) следовало бы запросить у владельца инфраструктуры; секреты в переписке не запрашиваются.
