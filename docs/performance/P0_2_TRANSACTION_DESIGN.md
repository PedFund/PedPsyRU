# P0-2 — проект сокращения транзакций при сохранении ответа

**Статус:** проектирование. Не реализовано; требуется отдельное согласование конкретного изменения (решение владельца от 22.11.2026).
**Основание:** `docs/performance/README.md` F-2; после P0-1 остаточная задержка сохранения определяется очередью пула, а не чтением попыток.

---

## 1. Что происходит сейчас

Один `PUT /api/v2/participant/attempts/:id/draft` выполняет три независимые транзакции на трёх разных соединениях пула:

| Шаг | Код | Транзакция | Работа |
|---|---|---|---|
| 1 | `identity.ts` → `uow.context` | T1 | `assertRuntimeClient`, `session_actor`, контекст участника |
| 2 | `identity.ts` → `withSession` | T2 | `lock_participant_identity`, чтение попыток, аудит `session_read`, `touch_session` |
| 3 | `participant-api.ts` → `service.save` → `uow.run` | T3 | повторный `session_actor`, `lock_participant_scope`, чтение попытки/ответов, CAS-update, diff ответов, аудит, `touch_session` |

Итого: 3 `BEGIN/COMMIT`, 3 `pool.connect()`, 3 `assertRuntimeClient`, 2–3 `session_actor()`. При пуле 8 и 300 участниках это утраивает и число занятых соединений, и время удержания; отсюда очередь и p95 в секундах даже после P0-1.

Ключевые инварианты, которые нельзя потерять:

- проверка сессии и прав выполняется **под блокировкой** и повторно перед записью;
- порядок блокировок: credential → session → study → participant → scope попытки;
- CAS по `revision`, идемпотентность, обязательный аудит в той же транзакции;
- RLS остаётся включённой; runtime-роль не получает прямых прав на новые таблицы;
- `scrypt` и любые сетевые вызовы не выполняются внутри транзакции.

## 1.1. Обязательное измерение до реализации

Нельзя утверждать, что три транзакции объясняют оставшиеся 5.96 с p95. До изменения кода нужно разложить бюджет задержки на сборке P0-1 при 300 VU и убедиться, какая доля приходится на ожидание соединения, блокировки и SQL.

| Компонент | Инструмент | Как измерять |
|---|---|---|
| Ожидание соединения пула | временная инструментация `pool.connect()` (monotonic timer до/после) + `pool.waitingCount/totalCount/idleCount` каждые 250 мс | p50/p95 ожидания на checkout; доля запросов, ждавших > 50 мс |
| Длительность транзакции | `pg_stat_activity` (state, `xact_start`, `wait_event_type`, `wait_event`), выборка 100 мс | распределение длительности T1/T2/T3; число `idle in transaction` |
| Удержание блокировок | `log_lock_waits=on`, `pg_locks`, журнал `duration:` для `lock_participant_identity`/`lock_participant_scope` | число и длительность ожиданий; max |
| Длительность SQL | `log_min_duration_statement=0` на изолированном стенде (или `pg_stat_statements`, если включён) | сумма `duration` по префиксам запросов; p50/p95 на запрос |
| Node.js | `monitorEventLoopDelay`, CPU time, RSS | lag p95, вклад в общий бюджет |
| Клиент | access-лог приложения vs k6 | разрыв «клиент/сервер» (F-11) |

Требования к эксперименту: те же данные и сценарий `exam.js`, 300 VU, ramp 1 мин + hold ≥ 5 мин, не менее 3 прогонов; окно устойчивого состояния; сумма компонентов должна объяснять p50, а не только коррелировать.

Критерий решения:

- если ожидание соединения ≥ 50 % p50 — P0-2 обоснован и реализуется;
- если доминируют SQL/блокировки — план пересматривается (индексы, порядок блокировок, сокращение запросов), а не «объединить всё в одну транзакцию»;
- если доминирует event loop/сеть — отдельное исправление, P0-2 не внедряется.

Только после этого таблица «ожидаемый эффект» в разделе 2 становится проверяемой гипотезой, а не обещанием.

## 2. Предлагаемое изменение (вариант A, минимальный)

Объединить шаги 1–3 в **одну** транзакцию для пишущих маршрутов участника (`save`, `complete`, `result`, `read`, `form`, `retry`):

1. `pool.connect()`; `assertRuntimeClient` (или проверка при подключении, P0-3);
2. `BEGIN`; `set_config('app.session_hash',$1,true)`, `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`;
3. один `SELECT * FROM pedpsy.session_actor()` → контекст (credential/study/participant/version);
4. `lock_participant_identity()` (тот же порядок блокировок, что сейчас в T2);
5. `lock_participant_scope(attempt_id)`;
6. чтение попытки и ответов, валидация, CAS `UPDATE`, diff `responses`, аудит, `touch_session`;
7. `COMMIT`.

`identity.session` перестаёт быть отдельным вызовом для пишущих операций; для `GET /participant/session` (чтение списка попыток) можно оставить облегчённый путь, но с той же одной транзакцией.

Ожидаемый эффект (гипотеза, проверяется замером 1.1): 3 → 1 транзакция, 3 → 1 соединение, 3 → 1 `session_actor`, 3 → 1 `assertRuntimeClient`. При том же пуле число одновременно удерживаемых соединений на запрос падает, поэтому очередь может сократиться; конкретная величина p95 не заявляется до измерения.

Оценка: на стенде после P0-1 серверное p50 сохранения ~3.8 с при 300 VU и пуле 4; при устранении двух лишних удержаний соединения возможно кратное снижение, но это проверяется отдельным замером до реализации. Точная цифра не заявляется заранее.

## 3. Риски и как их закрыть

| Риск | Мера |
|---|---|
| Более длинная транзакция удерживает блокировки | Сохранить порядок блокировок; `lock_timeout=3000`, `statement_timeout=5000`; не выполнять scrypt/HTTP внутри |
| Отзыв сессии в середине операции | Повторная проверка `session_actor` после ожидания блокировки; при несовпадении — `401` и rollback |
| Потеря обязательного аудита | Аудит в той же транзакции; тест «без аудита commit невозможен» |
| Двойное завершение/гонка | CAS по `revision` и `status='draft'` не меняются; тесты конкурентного завершения и повторной отправки |
| Ошибка прав RLS | PG-тесты: чужой участник, чужое исследование, завершённая попытка, отсутствие сессии |
| Регрессия login/registration | Эти пути не входят в изменение; отдельные тесты остаются |

## 4. Тесты и приёмка

1. PG: сохранение/завершение/результат в одной транзакции; отзыв сессии между чтением и записью; конкурентные пары (один 200 + один 409); аудит обязателен.
2. HTTP: существующие `postgres-api`, `postgres-workspace`, `postgres-participant-stages`, `postgres-login-by-email`.
3. Нагрузка: `exam.js` 300 VU, те же данные; сравнение p50/p95/p99, 5xx, числа успешных сохранений с P0-1.
4. Инварианты: 0 потерь, 0 дублей, 0 смешивания.
5. Наблюдаемость: `xact_commit` на одно сохранение должно упасть с ~3 до ~1; `pg_stat_statements`/лог — после включения (P1-5).

---

## 5. Что не входит

- объединение запросов между разными HTTP-запросами и кэширование сессии между ними;
- перенос scrypt в транзакцию (запрещено) или изменение его параметров;
- изменение лимитов, RLS, CSRF, модели регистрации;
- горизонтальное масштабирование.
