| Параметр | Значение |

| Дата | 2026-11-22 |

> Все числа ниже — либо фактические результаты ранее выполненных прогонов на изолированном стенде, либо пороги, заданные в k6-сценариях. Расчётных и предполагаемых значений нет. ## 1. Цель и границы

**1.1 Цель.** Установить, при какой одновременной нагрузке платформа «МетодТест» сохраняет работоспособность, заданные задержки и целостность данных, и зафиксировать, при каких нагрузках она отказывает.

| Показатель | Целевой уровень |
|---|---|
| Одновременные регистрации | 200 |
| Одновременные входы | 200 |
| Одновременно проходящие методику | 300 |
| Перспектива (вне текущей приёмки) | 1000 |
| Предельные прогоны | до 500+ |

**1.2 Входит в объём.** Шесть типов испытаний (smoke, load, stress, spike, soak, breakpoint); сценарии A–E; проверка целостности БД после каждого прогона; протокол фиксации.

**1.3 Не входит.**
- Любая экстраполяция на Selectel и вывод о пропускной способности продакшна: среды различаются (раздел 3, раздел 9).
- Реальные персональные данные, реальная отправка писем, юридическая и научная приёмка.
- Деплой, изменение прод-конфигурации и миграций; изменение кода приложения и k6-сценариев (кроме отдельно согласованных правок).
- Оценка научной валидности методик и содержания форм.

**1.4 Термины.** VU — виртуальный пользователь k6; итерация — один цикл `default`-функции; p50/p95/p99 — перцентили `http_req_duration` по тегу запроса; 429 — отказ троттлинга; 5xx — серверная ошибка; RPS — запросов в секунду; bucket — окно счётчика троттлинга в `pedpsy.login_throttles`.

**2.4 Как измерить недостающее.**

| Показатель | Способ |
|---|---|
| p50/p99, RPS | разобрать `--out json` прогона по тегам `http_req_duration`/`http_reqs`; либо временно добавить пороги p(50)/p(99) (правка сценариев — отдельным согласованием) |
| CPU/RAM | `Get-Counter '\Processor(_Total)\% Processor Time'`, рабочий набор процессов `node`/`postgres`; на проде — `top`/`ps` |
| очередь соединений | `SELECT state, wait_event_type, wait_event, count(*) FROM pg_stat_activity GROUP BY 1,2,3 ORDER BY 4 DESC;` |
| пул приложения | HTTP-метрик пула нет (есть только `/health`); оценивать по числу backend-сессий и задержке; отдельная метрика — отдельная задача |
| длительность транзакций | `pg_stat_statements`, если расширение доступно; иначе `log_min_duration_statement` на стенде |
| 5xx вне D | счётчик по `response.status` в сценариях или фильтр по `--out json` |

## 3. Требования к изолированной среде

**3.1 Стенд и продакшн.**

| Параметр | Изолированный стенд | Продакшн Selectel |
|---|---|---|
| ОС / CPU | Windows, i9-9900KF, 8 ядер / 16 потоков | Linux, 2 vCPU AMD EPYC 7763 |
| RAM | 16 ГБ | 3,9 ГБ, без swap |
| Диск | не зафиксирован | 40 ГБ SSD |
| Node.js | версия на стенде не зафиксирована | 22.23.4 |
| PostgreSQL | 18.6 (Windows) | 18.6; `shared_buffers` 128 МБ, `max_connections` 100, `work_mem` 4 МБ |
| Пул приложения | 4 (`demoConfig`) | 8 |
| Прокси | нет (прямой API) | nginx, 2 воркера |
| Данные | 236 синтетических аккаунтов, 708 попыток в фикстурах, 1440 попыток в БД | 245 попыток |

**3.2 Обязательные требования к прогону.**
1. Тот же код, что зафиксирован в протоколе (коммит и состояние `loadtest/`).
2. Отдельная PostgreSQL и отдельная БД; `dataset_kind='demo'`; только синтетика.
3. Без реальных писем: доставка `synthetic`, адреса только `@example.test`; в outbox нет статуса `sent`.
4. Отдельные журналы и метка `RUN_ID`; журналы разных прогонов не смешиваются.
5. Повторяемость: одинаковые env, VU и длительности; снимок БД до и после.
6. Сброс bucket-ов троттлинга между прогонами: `DELETE FROM pedpsy.login_throttles;` — только на стенде, с фиксацией времени.
7. Запрет продакшна: `BASE_URL` только loopback; `assertSafeTarget()` (раздел 10).
8. Пул 4 и настройки PG стенда не меняются в ходе серии; любое изменение — в протокол.

**3.3 Сброс bucket-ов.** Выполняется перед каждым прогоном A/B/E и после серии. `login_throttles` — счётчики, не аудит; `access_audit_events` не удаляется (append-only). Отказы 429 за прогон считаются по окну времени от T0.

## 4. Сценарии A–E

Общие правила `lib/common.js`: у каждой сессии свой набор cookie в заголовке (cookie jar k6 принудительно очищается), CSRF — `x-pedpsy-csrf`, запись — с `Origin`; допустимые статусы 200/201/204/400/401/403/404/409/422/429/503; `BASE_URL` по умолчанию `http://127.0.0.1:4174`. Данные: `data/accounts.json` (236), `data/attempts.json` (708 попыток, вход по email и паролю), `data/participants.json` (236, по 20 пунктов `item_ids`).

Теги запросов: `Health`, `Preflight`, `RegistrationContext`, `RegistrationStart`, `RegistrationReceipt`, `RegistrationConfirm`, `Login`, `Session`, `Form`, `DraftRead`, `SaveDraft`, `ConcurrentSave`, `ReplaySave`, `Complete`, `ResultRead`.

**4.1 Сценарий A — регистрация (уровни 20/50/100/200).**
Исполнение: `registration.js`, `shared-iterations`, `vus=VUS`, `iterations=VUS`, `maxDuration` 10 мин.

| Шаг | Запрос |
|---|---|
| 1 | `GET /api/v2/registration/preflight` → `csrf` |
| 2 | `GET /api/v2/registration/context` → версия уведомления |
| 3 | `POST /api/v2/registration/start` (email, пароль, notice) |
| 4 | `POST /api/v2/registration/receipt` → `confirmation_token` |
| 5 | `POST /api/v2/registration/confirm` |

Env: `BASE_URL`, `INVITE_TOKEN`, `VUS`, `RUN_ID`, `CONTACT_NOTICE` (`contact-notice-v3`), `MAX_DURATION`. Email итерации: `reg-<RUN_ID>-<VU*1000+ITER>@example.test`; счётчики `registration_throttled`, `registration_rejected`.
Команда: `k6 run -e BASE_URL=http://127.0.0.1:4174 -e INVITE_TOKEN=<токен стенда> -e VUS=200 -e RUN_ID=<run> registration.js`.
Пороги сценария: `checks>0.98`, `RegistrationStart p95<15000`, `Receipt p95<2000`, `Confirm p95<2000`.
Критерии: 20/50/100 — 100 % (база); 200 — либо 100 % при согласованно поднятом лимите receipt, либо зафиксированные 100 × 429 как ожидаемый режим лимита (база). Ёмкостный вывод при 200 возможен только после изменения лимита с записью значения.

**4.2 Сценарий B — одновременный вход 200.**
Исполнение: `login.js`, `per-vu-iterations`, `vus=VUS`, `iterations=1`, все VU стартуют вместе, `maxDuration` 5 мин. Один VU — один аккаунт `accounts[(OFFSET+VU-1) % 236]`.
Env: `BASE_URL`, `VUS` (200), `OFFSET`, `MAX_DURATION`. Счётчики `login_throttled`, `login_failed`.
Команда: `k6 run -e BASE_URL=... -e VUS=200 -e OFFSET=0 login.js`.
Пороги: `checks>0.95`, `Login p95<30000`, `http_req_failed<0.02`.
Критерии: база 140/200 и 60 × 429. Режим на момент базовых измерений зафиксирован по окружению процесса: `PEDPSY_PILOT_LOGIN=1`, `PEDPSY_PILOT_LOGIN_LIMIT=900`, `PEDPSY_PILOT_LOGIN_CONCURRENCY=2`, очередь 512, таймаут 30 с (см. [исходный аудит, раздел 2.4](https://github.com/PedFund/PedPsyRU/blob/fc4b2c25abfe37dc4dcaec6690a87c4d398bbcbf/PERFORMANCE_AUDIT.md#24-ограничения-и-очереди)). Отказ 60/200 — это таймаут очереди scrypt, а не глобальный лимит 900/5 мин; при повторе разложить отказы по `access_audit_events` (7.4) и записать значения этих переменных. Логинов больше 236 за прогон быть не может без повторов аккаунтов (лимит 5/15 мин на аккаунт).

**4.3 Сценарий C — прохождение методики 100/200/300.**
Исполнение: `exam.js` → `createExam(THINK_MIN, THINK_MAX, OFFSET)`, `ramping-vus`: 5 мин до `VUS`, `HOLD` 15 мин, 1 мин до 0, `gracefulRampDown` 30 с.
Итерация: вход (один раз на VU), `GET .../form`, `GET .../<id>` (черновик), затем `PUT .../draft` с полным массивом ответов и `expected_revision`; при 409 — перечитывание; think time 5–10 с.
Env: `VUS` (100/200/300), `RAMP`, `HOLD`, `THINK_MIN`, `THINK_MAX`, `OFFSET`. Счётчики `draft_revision_conflict`, `draft_rejected`.
Команда: `k6 run -e VUS=300 -e RAMP=5m -e HOLD=15m -e THINK_MIN=5 -e THINK_MAX=10 exam.js`.
Пороги: `http_req_failed<0.01`, `SaveDraft p95<500`, `SaveDraft p99<1500`, `Login p95<30000`, `checks>0.99`.
Критерии: цель — p95 сохранения ≤ 500 мс. База: 100 VU — med 10,2 / p95 12,3 с; 300 VU — med 10,9 / p95 13,1 с; цель не выполняется. 200 VU — не измерено, выполнить в этой серии.

**4.4 Сценарий D — конкурентность, повтор, конфликт версий, второе устройство.**
Исполнение: `conflict.js`, `per-vu-iterations`, `VUS`=20, `iterations=1`, `maxDuration` 5 мин. На одну попытку: `http.batch` из двух одновременных `PUT /draft` с одной `expected_revision`; затем повтор того же тела (`ReplaySave`); затем вход «второго устройства» и чтение ревизии.
Env: `BASE_URL`, `VUS`, `OFFSET`. Счётчики `expected_revision_conflicts`, `duplicate_write_rejected`, `unexpected_server_errors`.
Пороги: `checks>0.95`, `unexpected_server_errors count==0` — прерывание при первом 5xx.
Критерии: ровно один 200 и один 409 в паре; повтор — 409; второе устройство видит ревизию не старше исходной; 5xx = 0 (база выполнена).

**4.5 Сценарий E — смешанная нагрузка.**
Исполнение: `mixed.js`, три сценария параллельно: регистрация `shared-iterations` 200 VU/200 итераций с 0 с, вход `per-vu-iterations` 100 VU с 10 с, экзамен `ramping-vus` 300 VU с 20 с (5 мин ramp, `HOLD` 10 мин, 1 мин спад).
Env: `REG_VUS`, `LOGIN_VUS`, `EXAM_VUS`, `HOLD`, `RUN_ID`, `INVITE_TOKEN`. Счётчики `mixed_registration_throttled`, `mixed_login_throttled`.
Пороги: `SaveDraft p95<1000`, `Login p95<30000`, `checks>0.95`.
Критерии: сохранение ответа у уже работающих участников не должно деградировать до уровня A/B; база отсутствует — прогон обязателен. 429 регистрации при 200 ожидаемы (лимит receipt 100/5 мин).

**4.6 Предельные прогоны (500+).**
Выполняются как исследовательские, вне приёмки: `exam.js -e VUS=500` (708 попыток фикстуры хватает), `stress.js`, `breakpoint.js` до `MAX_VUS=400`. Ограничения: 236 аккаунтов (вход), 708 попыток (повторный VU → 409), пул 4, лимит receipt 100/5 мин. Уровень 1000 недостижим на текущих фикстурах: нужно расширить `attempts.json` минимум до 1000 записей (в БД стенда 1440) и учесть лимит 5/15 мин на аккаунт — отдельное согласование.

**4.7 Вспомогательные файлы.** `debug*.js` (5 файлов) — диагностические, не вызывают `assertSafeTarget()`, в приёмочный набор не входят.

## 7. Методика проверки целостности

**7.1 Снимок до/после.** Выполняется на стенде до T0 и после прогона; сравниваются счётчики и дайджесты.

```sql
SELECT count(*) AS attempts, coalesce(sum(revision),0) AS revision_sum,
       md5(string_agg(id::text||':'||revision::text||':'||status, ',' ORDER BY id)) AS digest
FROM pedpsy.attempts;

SELECT count(*) AS responses,
       md5(string_agg(attempt_id::text||':'||item_id||':'||value, ',' ORDER BY attempt_id,item_id)) AS digest
FROM pedpsy.responses;

SELECT count(*) AS results, md5(string_agg(id::text, ',' ORDER BY id)) AS digest
FROM pedpsy.attempt_results;
```

**7.2 Инварианты.** Ожидаемые значения — нули.

```sql
SELECT count(*) AS dup_responses FROM (
  SELECT attempt_id,item_id FROM pedpsy.responses GROUP BY 1,2 HAVING count(*)>1) d;

SELECT count(*) AS orphan_responses FROM pedpsy.responses r
LEFT JOIN pedpsy.attempts a ON a.study_id=r.study_id AND a.id=r.attempt_id AND a.release_id=r.release_id
WHERE a.id IS NULL;

SELECT count(*) AS foreign_item_responses FROM pedpsy.responses r
LEFT JOIN pedpsy.release_items ri ON ri.release_id=r.release_id AND ri.item_id=r.item_id
WHERE ri.item_id IS NULL;

SELECT count(*) AS orphan_results FROM pedpsy.attempt_results x
LEFT JOIN pedpsy.attempts a ON a.study_id=x.study_id AND a.id=x.attempt_id
WHERE a.id IS NULL;

SELECT count(*) AS completed_without_result FROM pedpsy.attempts a
LEFT JOIN pedpsy.attempt_results x ON x.study_id=a.study_id AND x.attempt_id=a.id
WHERE a.status='completed' AND x.id IS NULL;

SELECT count(*) AS double_results FROM (
  SELECT study_id,attempt_id FROM pedpsy.attempt_results GROUP BY 1,2 HAVING count(*)>1) d;

SELECT count(*) AS completion_pointer_mismatch FROM pedpsy.attempts a
JOIN pedpsy.attempt_results x ON x.study_id=a.study_id AND x.attempt_id=a.id
WHERE a.status='completed' AND a.completion_result_id IS DISTINCT FROM x.id;
```

**7.3 Сверка результатов.**

| Сценарий | Ожидание | Проверка |
|---|---|---|
| A | число подтверждённых регистраций = прирост `participants`/`participant_credentials` | прирост строк после T0 |
| A (без писем) | нет отправленных писем | `SELECT count(*) FROM pedpsy.contact_confirmation_outbox WHERE status='sent';` → 0 |
| B | вход не меняет `attempts`/`responses` | дайджесты 7.1 не изменились |
| C | прирост `sum(revision)` = число успешных SaveDraft (HTTP 200) | снимок 7.1 против счётчика k6 |
| D | пары 200/409, повтор 409 | счётчики `expected_revision_conflicts`/`duplicate_write_rejected` + 7.2 |
| E | нет 5xx при сохранении, регистрация не ломает черновики | теги + 7.2 |
| completion | прирост `attempt_results` = число `scored`; completed = results | SQL + счётчики `attempts_scored`/`attempts_incomplete` |
| все | нет 429 в smoke | счётчики и `access_audit_events` по окну T0 |

**7.4 Атрибуция 429.** `SELECT action, reason, count(*) FROM pedpsy.access_audit_events WHERE at_ms >= :t0_ms GROUP BY 1,2 ORDER BY 3 DESC;` — разделяет лимит глобального bucket, лимит аккаунта и таймаут admission-очереди. В базовых измерениях это разделение не выполнялось.

**7.5 Границы.** Инварианты доказывают отсутствие дублей, сирот и потерянных результатов; научную корректность расчёта они не доказывают. Природа 25 × 422 (`INCOMPLETE_RESPONSES`) в базовых измерениях не разбиралась: `completion.js` отсекает черновики с числом ответов меньше `item_ids` до запроса, поэтому источник 422 нужно установить по данным (`responses` против `release_items`) отдельно.

## 8. Протокол фиксации

**8.1 Поля.**

| Поле | Содержание |
|---|---|
| Идентификация | `RUN_ID`, дата/время (часовой пояс), оператор |
| Код | коммит, ветка, статус `loadtest/` |
| Среда | версия Node, версия k6, ОС, PostgreSQL и настройки, пул, nginx (для прода) |
| Параметры | `BASE_URL` (хост), `INVITE_TOKEN` (метка, не значение), env, executor, VU, этапы, длительность |
| Результаты | p50/p95/p99, RPS, `checks`, `http_req_failed`, счётчики 429/5xx/409/422 |
| БД | снимок 7.1, инварианты 7.2, сверка 7.3 |
| Аномалии | всплески, ретраи, ручные вмешательства, сбросы bucket-ов |

**8.2 Форма записи.**

```text
RUN_ID: ...            Дата/время: ... (TZ)
Коммит: ...            Ветка: ...    loadtest: <коммит/статус>
Node: ...  k6: ...     ОС: ...       PostgreSQL: ...
BASE_URL: ...          Пул: 4        VU/этапы: ...
Длительность: ...      Сброс throttles: <время>
p50/p95/p99: ...       RPS: ...      checks: ...  failed: ...
429: ...  5xx: ...    409: ...      422: ...
Инварианты: dup=.. orphan=.. foreign=.. orphan_results=.. completed_without_result=.. double=..
Аномалии: ...
```

**8.3 Хранение.** Сырые выгрузки (`--out json`) и журналы — на стенде, вне Git; в Git — только агрегированный протокол без токенов и паролей. Синтетические адреса `@example.test` публиковать допустимо; реальные данные — никогда.

**8.4 Состояние набора.** На момент подготовки плана каталог `loadtest/` не отслеживается Git (`git status`: `?? loadtest/`). До серии его нужно зафиксировать коммитом, иначе коммит в протоколе не будет соответствовать запущенному коду. Набор не содержит `handleSummary`; для архива использовать `--out json=<файл>` и сохранённый stdout.

## 9. Риски и ограничения

| Риск | Влияние | Мера |
|---|---|---|
| Объём данных: 1440 попыток в БД стенда против 245 на проде | абсолютные задержки не переносятся; сравнение только относительное | фиксировать объём в протоколе; не экстраполировать |
| k6 и приложение на одном хосте | генератор отнимает CPU у приложения, задержки завышены | измерить CPU k6; по возможности вынести генератор; учитывать при выводах |
| Пул 4 на стенде против 8 на проде | очередь соединений наступает раньше | не переносить пороги; сравнивать сценарии между собой |
| 3,9 ГБ RAM и no swap на проде, 16 ГБ на стенде | OOM-риск не воспроизводится; scrypt ~128 МБ на операцию | отдельный вывод: стенд не доказывает устойчивость по памяти |
| Windows vs Linux, иные настройки PG, nginx на проде | таймауты, планировщик, буферизация | различия фиксировать; не смешивать прогоны стенда и прода |
| Троттлинг: A200 — 100 × 429, B200 — 60 × 429 | тест измеряет лимитер, а не ёмкость | согласованный подъём лимита с записью значения; разделять причины 429 |
| 236 аккаунтов и 708 попыток в фикстурах | >236 логинов — повторы; >708 VU — коллизии; 1000 недостижимо | уровни в пределах фикстур; расширение данных отдельным решением |
| Нет метрик CPU/RAM/пула/транзакций | нельзя объяснить причину задержек | раздел 2.4; профилирование отдельной задачей |
| Повторный прогон меняет `revision` и результаты | сверка до/после искажается | снимок БД, `OFFSET`, отдельные прогоны на клон |
| Один attempt в разных прогонах | 409 не по причине нагрузки | уникальные срезы `OFFSET` и сброс состояния |
| Денилист в safety-gate | любой другой хост при `ALLOW_NON_LOCAL=1` будет принят | решение о запуске — за оператором; хост фиксируется в протоколе |

## 10. Чек-лист и safety-gate

**10.1 Перед запуском.**
- [ ] Коммит и состояние `loadtest/` зафиксированы; набор в Git.
- [ ] `BASE_URL` — loopback; `GET /health` → 200.
- [ ] `GET /api/v2/registration/preflight` → 200 и `csrf`; иначе A/E невалидны (сценарий считает это `rejected`, а не отказом стенда).
- [ ] `INVITE_TOKEN` действует; в протокол — метка, не значение.
- [ ] БД стенда: `dataset_kind='demo'`, пул 4, настройки PG записаны.
- [ ] Нет реальных адресов: outbox и контакты дают только `@example.test`.
- [ ] Bucket-ы сброшены, время T0 записано.
- [ ] Снимок 7.1 сохранён.
- [ ] Свободны CPU/RAM; другие нагрузки не идут; окно согласовано.
- [ ] Журналы отдельные, `RUN_ID` задан.
- [ ] `smoke.js` зелёный; пороги не нарушены.

**10.2 Safety-gate (`assertSafeTarget`).**
- Вызывается при инициализации `smoke.js`, `registration.js`, `login.js`, `exam.js`, `stress.js`, `spike.js`, `soak.js`, `breakpoint.js`, `conflict.js`, `completion.js`, `mixed.js`; при отказе k6 завершается до отправки трафика.
- Запрещённые хосты: `mettest.vibemind.pro`, `vibemind.pro` и их поддомены — безусловный отказ.
- Не-loopback хост без `ALLOW_NON_LOCAL=1` — отказ. `ALLOW_NON_LOCAL=1` допустим только для изолированного стенда с письменным подтверждением; значение и хост — в протокол.
- Список запрещённых хостов — денилист, а не allowlist: ответственность за выбор цели остаётся на операторе. Production запрещён при любых значениях env.
- Критерии немедленной остановки: любой 5xx в сценарии D, нарушение инварианта 7.2, 429 в smoke, падение Node, нехватка памяти, выход за пределы согласованного окна.
- `debug*.js` не вызывают gate и в прогонах не используются.

**10.3 После прогона.**
- [ ] Снимок 7.1 и инварианты 7.2 (все нули).
- [ ] Сверка 7.3 по сценарию; 429 атрибутированы.
- [ ] Протокол 8.2 заполнен; результаты приложены.
- [ ] Bucket-ы сброшены; стенд оставлен в исходном состоянии; прод не затронут.
