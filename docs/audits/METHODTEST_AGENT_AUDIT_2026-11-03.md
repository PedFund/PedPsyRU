## 2. Проблема, остановившая Codex

Наблюдения из журнала:

- CI_BROWSER_STATE_TIMEOUT / researcher method catalogue: methodChoices=0, methodEnabled=0; JS-ошибки не зафиксированы.
- CI_BROWSER_STATE_TIMEOUT / constructor groups and stage: methodChoices=0, methodEnabled=0.

Контракт:

1. src/ports/studies.ts определяет StudyDesign.catalog как список разрешенных выпусков ConstructorRelease с id и method_id.
2. web/workspace/app.js, renderMethodCatalog(), перебирает libraryMethods, а затем ищет точное соответствие release_id в design.catalog.
3. tests/postgres-fixture.js импортирует учебный выпуск ТКИ, но не гарантирует запись с его метаданными в отдельном method_library_catalog.
4. tests/postgres-method-library.integration.js проверяет, что каталог метаданных может возвращать пустой список до связывания записи с выпуском ТКИ.
5. web/workspace/method-search.js предполагает массивы indicators, subscales, outputs и search_terms; fallback должен сохранять корректный контракт.

**Рабочая гипотеза:** пустой UI вызван обязательной зависимостью рендеринга от отдельной библиотеки метаданных, даже если список разрешенных выпусков непуст. Гипотеза основана на статическом анализе и CI; без адресного воспроизведения ее нельзя объявлять доказанной первопричиной.

Проверить в одном синтетическом тесте фактические размеры и содержимое design.catalog, libraryMethods и planningMethods, а также ответы API /api/v2/researcher/methods и /api/v2/researcher/studies/:id/workbench. Сопоставить release_id с id и method_id. Не скрывать сбой путем удаления проверок.

## 3. Безопасный порядок продолжения

**Первое:** в журнале остановленного Codex указаны четыре незакоммиченных файла (+7/−7), среди них tests/browser-fixture.js, tests/postgres-workspace-browser.integration.js, web/workspace/app.js. Их содержимое не видно в GitHub. Не выполнять reset/rebase/clean, не перезаписывать рабочую копию Windows и не публиковать поверх них непроверенный патч.

**Второе:** воспроизвести оба браузерных сценария на одноразовой базе pedpsy_ci_*. Измерить ответы API и проверить, что серверный набор разрешенных выпусков и метаданные действительно расходятся.

**Третье:** выбрать минимальное исправление по фактическому контракту. Возможный вариант: источником разрешений остается серверный design.catalog, метаданные подтягиваются при точном совпадении и при их отсутствии применяется безопасный нейтральный fallback. Альтернатива – заполнение фикстуры метаданными, если продуктовый контракт требует обязательную полноту. Решение закрепить тестом с synthetic-TKI-only.

**Четвертое:** запустить адресные тесты и проверки синтаксиса/типов, затем npm test и полный npm run test:pg, после этого GitHub Actions на точном commit SHA. Проверить три обязательных независимых браузерных повтора. Не ослаблять проверки.

**Пятое:** только после полностью зеленого CI проверить порядок интеграции stacked PR №63 и №64, совместимость миграций, резервную копию и актуальный main. Ни merge, ни развертывание, ни изменение рабочей PostgreSQL, ни отправку писем не выполнять без отдельного решения владельца.

## 6. Как уменьшить расход и правильно передавать работу агенту

1. Передавать короткую контрольную точку с точными base/head SHA, двумя failing tests и ограничениями.
2. Начинать с 5–8 относящихся к дефекту файлов, не загружать весь репозиторий заново на каждом шаге.
3. Из полного журнала CI передавать два failing blocks и несколько строк контекста.
4. Сначала выполнять быстрые адресные проверки, затем полный регрессионный набор и один CI.
5. Разделять диагностику, правку, тестирование и публикацию PR на небольшие завершенные задачи.
6. Перед следующей сессией фиксировать принятое решение, результаты и фактический расход.
