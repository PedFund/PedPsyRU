# МетодТест – автономная разработка, экспериментальная конфигурация

Дата создания: 2026-11-23. Это начальная инфраструктура, а **не** уже запущенная команда ИИ-агентов.
Существующие PR и рабочий сервер остаются без изменений.

## Контрольные точки

- main до начала установки: `444cd88477e5c5ea251a1f54ef5f78694056fc85`, ветка `checkpoint/pre-autonomy-main-20261123`.
- PR #204 на момент начала: `7bfdf99b20e73da55c8d645d259954367e1f36c5`, ветка `checkpoint/pr204-head-20261123`.
- PR #204 – номер запроса на объединение, **не номер коммита**. Ветки сохраняют только Git-объекты. Они не являются резервными копиями PostgreSQL, файлов или секретов.
- После применения миграций нельзя откатываться путем одного `git reset`: требуется проверенный backup/restore, совместимость приложения с БД и отдельное решение владельца.

## Предлагаемый цикл

1. **Оркестратор** проверяет `AGENTS.md`, текущий `main`, открытые PR и зависимости; берет только задачу, явно помеченную для автономного цикла. Одна небольшая задача на PR. Никаких скрытых дополнительных фаз.
2. **Разработчик (DeepSeek Harness)** создает `agent/<issue>-<topic>` от актуального `main`, меняет минимальный набор файлов, проверяет diff и готовит PR. Не пушит в `main`.
3. **Тестировщик** запускает адресные, регрессионные и при необходимости изолированные PostgreSQL/браузерные тесты. Не запускает 200–300 VU на Windows 10 (16 ГБ).
4. **Независимый ревьюер**, использующий отдельную GitHub-личность, проверяет изменения и результаты, включая научные и security-инварианты. Одобрение привязано к точному head SHA; любое изменение отменяет прежнюю приемку.
5. **GitHub Actions** проверяет все необходимые задания CI, принадлежность репозиторию, защищенность `main`, чистоту Merge, текущую базу, допустимые файлы и одобрение независимого ревьюера.
6. Только одобренный PR из низкорискового allowlist может быть объединен в `main` автоматически. После каждого Merge система заново оценивает следующий PR.
7. Оркестратор фиксирует результат в Issue/PR. При блокере создает запись и останавливается, не расширяя полномочия.

## Что реально реализует этот PR

- `scripts/autonomy-policy.mjs` – строгая политика низкорисковых PR.
- `tests/autonomy-policy.test.js` – положительные и отрицательные проверки политики.
- `scripts/autonomy-gate.mjs` – проверяет реальные PR в GitHub; по умолчанию только аудит; при явном включении может объединить один допустимый PR.
- `.github/workflows/autonomy-gate.yml` – плановый read-only аудит раз в 2 часа и вручную; отдельное задание Merge с разрешениями на запись.
- Ни один из этих файлов не запускает DeepSeek и не меняет рабочий Selectel.

## Первоначальная автоматическая область

- Не более пяти измененных файлов и не более 250 добавленных строк.
- Только `web/workspace/*.css` и `docs/ui/*.md`.
- Нет удаления/переименования, недоступных больших патчей и потенциально опасного CSS с `url()`, `@import` и аналогичными конструкциями.
- Ветка начинается с `agent/`, создана в том же репозитории; PR имеет метки `autonomy:auto-merge` и `autonomy:reviewed`.
- Требуются независимое **APPROVED** ревью точного SHA, полный CI с успешными шестью работами, чистый PR и защищенная `main`.

**Не входят в автоматический Merge:** изменения JS/TypeScript, Node.js, регистрации, доступа, миграций, SQL, интерфейсов с HTML/JS, ключей и форм психодиагностики, методических норм, тестов, security-конфигурации, GitHub workflows. Такие PR оформляются и проверяются агентами, но объединяются только по отдельному решению владельца. Ограничение можно расширять по результатам аудита.

## Что необходимо отдельно включить владельцу

1. В GitHub `Settings → Branches` или `Settings → Rules → Rulesets` защитить `main`: требовать Pull Request, успешные обязательные проверки `Required checks` (и применимые проверки безопасности), выбрать **Require branches to be up to date before merging**, запретить force-push, запретить удаление ветки. Запретить обход этих правил администраторами и ботами, если доступна соответствующая настройка. Убедиться, что администратор и боты не обходят ограничения.
2. Настроить отдельную GitHub-личность или GitHub App для независимого ревью; нельзя считать собственный текст агента в PR независимым APPROVED.
3. Создать контролируемый облачный исполнитель для DeepSeek Harness с ограниченными credentials. Не использовать Windows 10 как обязательный постоянно работающий сервер. Хранить API-ключ в защищенных secrets runner, не в репозитории. Ограничить задачи по времени, числу попыток (не более двух автоматических исправлений) и расходам API.
4. Выполнить **тест на одной синтетической CSS-задаче** от создания Issue до зеленого CI, независимого одобрения и сухого отчета `Autonomy PR gate`.
5. Только после этого установить в `Settings → Secrets and variables → Actions → Variables` переменную `AUTONOMY_AUTOMERGE_ENABLED=true`. До этого шага workflow никогда не объединит PR.
6. Для проверки вручную: `Actions → Autonomy PR gate → Run workflow → report`; это безвредная проверка. Режим `merge` также требует переменную и остальные условия.

## Границы и блокеры

- **Сейчас развернут только механизм контрольного аудита и будущего Merge.** Нет настроенного постоянно работающего облачного DeepSeek Harness, отдельного reviewer-аккаунта и защищенной `main`. Нельзя обещать выполнение задач без пользователя до настройки этих компонентов.
- Старые PR #199, #202, #204 не получают автоматический Merge; это задача отдельной интеграции с зависимостями и миграциями.
- Deploy, Selectel, рабочая PostgreSQL, SMTP, реальные учетные записи и любые платные ресурсы – не входят в автономный контур.
- Никаких реальных ПДн и результатов; только синтетические данные.
- Отчет по каждому циклу: Issue, PR, SHA, тесты, CI, review, Merge, блокеры, затраты и решения владельца.
- Для экстренной остановки: удалить/поставить в false `AUTONOMY_AUTOMERGE_ENABLED`; остановить исполнитель Harness; отозвать его токены. GitHub не откатывает уже выполненные слияния сам.
