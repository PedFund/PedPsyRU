# Runbook реагирования на инцидент и утечку ПДн

Дата: 2026-11-17. Основание: 152-ФЗ ст. 21 ч. 3.1 (уведомление РКН), 420-ФЗ (ответственность), приказ ФСТЭК № 21 (реагирование), методика У_зи (направление «реагирование на инциденты» — текущий уровень 0). Связанные документы: [THREAT_MODEL.md](THREAT_MODEL.md), [DATA_INVENTORY.md](DATA_INVENTORY.md), [MATURITY_BASELINE.md](MATURITY_BASELINE.md).

Статус: рабочий черновик для оператора. Роли и контакты заполняет владелец; до заполнения runbook нельзя считать готовым к применению.

## 1. Роли и границы

| Роль | Кто | Ответственность |
|---|---|---|
| Владелец (оператор) | [указать] | решение об уведомлениях, внешние коммуникации, разрешение на действия с рабочей БД |
| Ответственный за ИБ | [указать] | ведёт инцидент, фиксирует факты, готовит уведомление |
| Технический исполнитель | [указать] | сбор фактов, локализация, восстановление |
| Подрядчики | Selectel (хостинг/БД/SMTP) | уведомляют о своих инцидентах по договору [указать реквизиты DPA] |

Правила: не удалять логи и аудит, не переписывать историю, не выполнять массовые сбросы паролей и не менять рабочую БД без разрешения владельца; все действия фиксировать с временем (UTC) и исполнителем.

## 2. Классификация

| Уровень | Признак | Реакция |
|---|---|---|
| S1 | Подтверждённая утечка ПДн, компрометация БД/бэкапа, доступ постороннего к данным | Немедленно; уведомление РКН в 24 ч |
| S2 | Подозрение на компрометацию (аномалия в аудите, чужой вход, утечка секрета) | В течение 1 часа; проверка и решение по S1 |
| S3 | Отказ сервиса, DoS, ошибка без признаков доступа к ПДн | В рабочий день; фиксируется, но не уведомление РКН |
| S4 | Событие без последствий (попытка, заблокирована) | Регистрируется, разбор по графику |

## 3. Порядок действий

### Шаг 1. Обнаружение и регистрация (0–30 минут)

Источники: аудит `access_audit_events` (отказы, троттлинг), `contact_confirmation_outbox` (аномалии отправки), жалобы участников, письма Selectel, мониторинг.

Действия: завести запись инцидента (ID, время, источник, первые факты), назначить ответственного, зафиксировать текущее время UTC.

```sql
-- последние отказы и аномалии (синтетическая проверка запроса, не выгрузка ПДн)
SELECT at_ms, action, outcome, reason, actor_role, resource_id
  FROM pedpsy.access_audit_events
 WHERE at_ms > (extract(epoch FROM now())*1000)::bigint - 86400000
 ORDER BY at_ms DESC LIMIT 200;
-- состояние почтового контура
SELECT status, count(*) FROM pedpsy.contact_confirmation_outbox GROUP BY 1;
```

### Шаг 2. Локализация (0–2 часа)

- Отозвать активные сессии подозрительных учётных записей (не удалять их).
- При компрометации секрета — ротация ключа (MFA/контактов/SMTP) через файл, не через чат.
- При подозрении на доступ к БД — ограничить сетевой доступ к PostgreSQL, не останавливая сервис без необходимости.
- Зафиксировать, какие действия предприняты, и время.

### Шаг 3. Сбор фактов (0–6 часов)

Сохранить (не изменяя): выгрузку аудита за период, журналы сервиса, состояние outbox, снимок БД для разбора в изолированной среде.

```bash
journalctl -u mettest --since '<начало>' --no-pager > /var/backups/mettest/incident-<id>-service.log
pg_dump -Fc -d pedpsy_staging_5c1e8a7b3d9f4026 > /var/backups/mettest/incident-<id>.dump
sha256sum /var/backups/mettest/incident-<id>-* > /var/backups/mettest/incident-<id>.sha256
```

Требования: файлы 600, копии не покидают контур без решения владельца; в переписке и тикетах не публиковать реальные email/ответы.

### Шаг 4. Оценка объёма (к 12 часам)

Ответить письменно: какие категории ПДн затронуты, сколько субъектов, какие исследования, есть ли специальные категории (по текущему профилю — нет), затронуты ли несовершеннолетние (по политике — нет; проверять по данным), затронуты ли backups.

```sql
-- затронутые субъекты по исследованию (только количество, без выгрузки)
SELECT study_id, count(DISTINCT participant_id) FROM pedpsy.participant_contacts
 WHERE study_id = '<study>' AND status='active' GROUP BY 1;
```

### Шаг 5. Уведомления (24 и 72 часа)

- **24 часа** с момента обнаружения — уведомить Роскомнадзор о факте утечки (если подтверждена или высока вероятность).
- **72 часа** — результаты внутреннего расследования и сведения об устранении.
- Уведомление субъектам — если требуется по характеру данных; текст согласуется с владельцем.
- Уведомление подрядчиков/партнёров — по договору.

Формы и каналы: [указать личный кабинет/форма РКН, ответственного за отправку]. Факт и время отправки фиксируются в карточке инцидента.

### Шаг 6. Устранение и восстановление (после локализации)

- Исправить причину (код, конфигурация, права, секрет), выпустить через ветку → PR → CI → разрешение владельца.
- Восстановление из backup — только по согласованию и с проверкой целостности (`pg_restore --list`, sha256).
- Проверить `/health`, аудит, отправку писем, вход участника на синтетическом сценарии.

### Шаг 7. Разбор (до 10 рабочих дней)

Хронология, корневая причина, что сработало и что нет, какие меры добавить, обновление модели угроз и оценки У_зи, проверка сроков 24/72.

## 5. Что нельзя делать

- Удалять логи, аудит, «подчищать» записи и переписывать историю результатов.
- Менять пароли всем участникам и блокировать исследования без решения владельца.
- Публиковать в тикетах и чатах реальные email, ответы, результаты, ключи.
- Работать с рабочей БД деструктивно до фиксации фактов и backup.

## 6. Ограничения

Runbook не заменяет инструкции оператора и договоры с подрядчиками. Сроки 24/72 ч относятся к уведомлению РКН и не отменяют внутренних обязательств. До заполнения разделов «[указать]» готовность оценивается как неполная.
