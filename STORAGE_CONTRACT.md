## Состояние

Будущий серверный черновик: `attempt_id`, `status`, `revision`, `release_id`, точные версии, `current_item_id`, `responses[]`. Ответы — по ID, не по текстам/номеру слайда. Выпуск выбирает серверное назначение, клиент его не меняет. Участник и область исследования определяются индивидуальной сессией. Проверка доступа предшествует чтению, записи и расчету.

## Операции

Логический контракт будущих операций. Чтение существующей своей попытки частично реализовано в 01д.3а (GET /api/participant/attempts/:id); создание/запись/завершение/очистка не открыты. Точные маршруты записи/JSON Schema/HTTP-коды определяются в соответствующих следующих задачах.

| Операция | Вход | Результат | Ограничения |
|---|---|---|---|
| Получить/создать попытку | Назначение в области участника | Существующий draft/completed либо одна новая draft, revision=0, первый item, пустые ответы | Уникальность и транзакция предотвращают две строки при одновременном входе |
| Прочитать состояние | ID своей попытки | Ответы, слайд, revision, версии; для completed — разрешенный сохраненный результат | Не выдавать чужие данные/ключ/credentials |
| Сохранить черновик | expected_revision, полный текущий responses[], current_item_id | Атомарная замена снимка и revision+1 | Только draft, допустимые ID/A/B; неуказанные пары остаются пропусками |
| Завершить | expected_revision | Одна completed и серверный result | Только сохраненный полный протокол; при ошибке остается draft |
| Очистить черновик | expected_revision, подтверждение UI | Пустые ответы, первый item, revision+1 | Только свой draft; completed не удаляется кнопкой прохождения |

Сохраняется полный снимок максимум 30 ответов TKI, не произвольный merge. Ответы, позиция и revision изменяются одной транзакцией. Дубликаты/неизвестные ID, кириллические А/Б, неверный слайд или подмена версий отклоняются без изменения состояния.

## Автосохранение и две вкладки

Изменение ответа/слайда сохраняется с последней подтвержденной revision. Операции страницы идут последовательно; быстрые изменения можно объединить в следующий снимок, но нельзя переставлять запросы. UI различает «сохраняется», «сохранено» и «не сохранено».

Ответ сервера подтверждает только отправленный снимок. Более свежий выбор не объявляется сохраненным до своего подтверждения. Завершение сначала дожидается записи последнего снимка и использует ее revision.

При конфликте expected_revision сервер не перезаписывает данные. Клиент предлагает получить актуальный черновик, не затирает другую вкладку и не объединяет ответы автоматически. При неопределенном исходе сетевого запроса сначала перечитать состояние; слепой повтор со старой revision не считается сохранением.

После закрытия восстанавливаются только подтвержденные сервером ответы и позиция. Нельзя обещать восстановление несохраненного изменения при обрыве сети. Диагностические данные не помещаются скрыто в localStorage как обход ошибки сервера.

## Атомарное завершение

1. Проверить индивидуальный доступ, назначение и область.
2. Получить согласованное состояние попытки в транзакционной границе. Для completed вернуть существующий результат без новой строки/расчета.
3. Для draft проверить expected_revision и прочитать сохраненный снимок.
4. Вызвать существующий `scoreTki` с закрепленными сервером версиями. Клиентские баллы не принимать.
5. При incomplete/invalid/blocked/error не создавать result и не переводить в completed.
6. Для scored атомарно создать единственный result, зафиксировать input_revision, версии, key_digest, responses_digest, полный payload и completed_at, обновить status/revision.
7. При повторе/гонке вернуть ту же фиксацию. Сбой транзакции не оставляет completed без результата или результат без completed.

`responses_digest` строится из `{item_id,value}` в порядке выпуска, не клиентского массива. Функция/canonical-json-v1 реализованы и проверены в 01д.2, но сервис результата ими еще не пользуется. Digest — контроль воспроизводимости, не анонимизация и не credential; исследователю по умолчанию не выдается.

Черновики/возобновление — 01д.4; атомарный сохраненный результат — отдельная задача 01е. Нынешний технический просмотр не заменяет ее.

## Приемочные сценарии следующих задач

| Проверка | Ожидаемый результат |
|---|---|
| Повторный вход по тому же назначению | Тот же attempt_id, не новая запись |
| Сохранить ответы и q08; перезапустить сервер/страницу | После разрешенного входа восстановлены подтвержденные ответы и q08 |
| Две вкладки пишут одну revision | Одна успешна, другая получает конфликт; нет потери обновления |
| Потерян ответ API после успешной записи | Перечитывание подтверждает фактическую revision |
| Неполный/дублированный/недопустимый протокол | Нет result и completed |
| Двойное/одновременное завершение | Один result с тем же ID и баллами |
| Сбой фиксации | Согласованная попытка, повтор без дубликата |
| Изменение/очистка completed | Отказ, результат не меняется |
| Подмена чужого ID | Отказ до выдачи ответов/баллов |
| Создание T1 по T0 | Настройки можно копировать, ответы/результаты нельзя |
| Подмена режима на real | Тренировочный контур не переключается клиентом |

В 01д.4 проверены повторный вход/тот же ID, ответы/q08/reopen, две вкладки, потерянный ответ API, отказ записи/очистки completed, чужой ID, отсутствие наследования T0 и клиентского real. Invalid/неполный draft не создает result/completed; SQL/audit сбои откатывают снимок. Двойное/одновременное завершение и прикладная фиксация результата еще не реализованы и не проверены. В Git только вымышленные fixtures, без действующих credentials и реальных данных.
