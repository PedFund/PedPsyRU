# Расширяемое подключение методик

Решение владельца от 29.10.2026: не ограничивать библиотеку несколькими типами тестов. Для новой методики допустим отдельный программный модуль, включая собственные задания, обработку и результаты.

## Два пути подключения

1. Обычные опросники используют общий экран выбора ответа и адаптер последовательного прохождения. ТКИ и Карпов уже включены в этот путь.
2. Любая другая процедура получает отдельный модуль: например, ранжирование, матрица, последовательность событий со временем, ветвящееся задание, ответ с файлом или ручной оценкой. Типы не перечисляются в закрытом enum. Методика сама определяет допустимые данные и завершённость.

`src/ports/method-runtime.ts` — открытый контракт, `src/scoring/method-runtime.ts` — реестр и запуск. `src/scoring/builtin-instrument-modules.ts` содержит явно подключённые совместимые модули. Расчёт действующего participant service проходит через этот реестр. `src/adapters/pinned-instrument-releases.ts` отделяет закреплённые формы от транзакций и проверки прав. `web/workspace/method-presenters.js` отдельно регистрирует версии экранов; текущий экран вопросов использует этот реестр.

## Предъявление участнику

- **Последовательная методика** (опросник, набор вопросов) — один пункт на экран, кнопки «Назад / Далее» и индикатор прогресса. Не показывать несколько пунктов сразу.
- **Целостная методика** (ранжирование, матрица, единый стимул) — весь материал на одном экране. Не разбивать её на страницы по числу пунктов.
- Режим задаётся `presentation` в форме выпуска. Если `presentation` отсутствует, используется последовательный `pedpsy/single-choice`. Для целостной формы нужен явный версионированный экран, а не эвристика.
- Текущее состояние: CO-36 — `pedpsy/ranking-grid` (все 36 на одном экране); остальные 10 выпусков `approved/v1` и TKI — последовательные.

## Состав модуля

| Часть | Что хранит или делает |
| --- | --- |
| Идентификаторы | Версии контракта, методики, обработчика и digest ключа |
| Карточка | Название, авторы, имена и виды всех получаемых показателей |
| Схема ответа | Собственный идентификатор/версия; значения JSON любой вложенной структуры |
| Экран | Явно установленный компонент с собственным идентификатором/версией |
| Проверка черновика | Допустимость и завершённость по правилам конкретной процедуры |
| Обработка | Функция модуля; общая платформа не предполагает сумму или четыре алгоритма |
| Схема результата | Собственные числа, категории, профили, таблицы, текст, статус ожидания ручной оценки |
| Представление участнику | Явная отдельная проекция результата |

Общий контракт допускает произвольный JSON, а не только массив `q01 → A/B`. Например, `{state:{visited:[...]}, responses:[...], events:[{stimulus,ms,correct}]}`. Ссылки на рисунки/файлы должны быть внутренними идентификаторами объектов с самостоятельной проверкой владельца; сами файлы, загрузчик и внешние URL не исполняются через JSON. Ручная оценка может возвращать `pending_review`: её нельзя превращать в готовый числовой балл.

## Границы совместимости

Существующий контракт пакетов **1.0** и PostgreSQL-прохождений с одиночным выбором сохранён. Его ограничения относятся только к этому адаптеру, а не ко всем будущим методикам. Версии старых форм, ключей и завершённые результаты не переписываются.

Новый открытый runtime — действующий программный интерфейс, **не универсальный пользовательский загрузчик готовых тестов**. Для новой нестандартной методики разработчик отдельно подключает её экран и адаптер сохранения/HTTP, а также проверяет допуск, доступ и продолжение с сохранённого состояния. Сейчас публичный HTTP и SQL online-контур реализован только для ТКИ и Карпова. Загрузка рисунков, серверное измерение времени, интерфейс эксперта и адаптивный маршрут ещё не являются готовыми пользовательскими функциями. Контракт и синтетические тесты показывают, что их ответы и результаты не требуется подгонять под шкалу 1–7 или алгоритм суммы.

## Порядок добавления следующей методики

1. Зафиксировать конкретную авторскую версию, бланк, ключ и ожидаемые выходные показатели; не угадывать недостающую адаптацию.
2. Выбрать существующий адаптер прохождения либо реализовать отдельный. Схемы ответа, результата и экрана имеют независимые версии.
3. Добавить модуль в явную композицию сервера и его экран в композицию браузера. Код из загруженного JSON/архивного JS не запускается автоматически.
4. Добавить проверенные контрольные примеры и негативные случаи. Проверить незавершённость, возобновление, повтор завершения и область доступа.
5. Явно закрепить разрешённый выпуск в хранилище и каталоге. Наличие описания или обработчика само по себе не разрешает назначение.

Разные версии одного теста могут сосуществовать. Неизвестный обработчик, другая версия или другой digest отвергаются; случайный переход на «похожий» тест исключён. Данные копируются и замораживаются на границах модулей; циклы, функции, getters, небезопасные ключи, NaN/Infinity и чрезмерные размеры отвергаются. Ограничения размера/глубины — технические лимиты транспорта, не ограничение числа семейств методик.

## Переносимость

Описание, исходники модулей, формы, ключи и миграции находятся в проекте; серверная часть использует обычные Node.js и PostgreSQL. Отдельного сервиса Windows, привязки к диску P: или специфического облачного API не добавлено. Для Selectel переносятся та же сборка и БД с соответствующим резервным копированием; файлы будущих медийных методик потребуют собственного хранилища объектов и восстановления. Настройка облака в эту работу не входит.

## Проверка

`tests/method-runtime.test.js` проверяет пять несовместимых форматов данных, ожидание ручной оценки, неверные версии/ключи, изоляцию проекции, неизменяемость и совпадение результатов прежних обработчиков. `tests/postgres-karpov-online.integration.js` проверяет совместное назначение ТКИ/Карпова, сохранение и продолжение, CAS, чужие ответы и роли, откат при ошибке аудита, идемпотентное завершение, собственный результат и отсутствие индивидуальных баллов в researcher progress. Полный pg_dump/pg_restore в тесте библиотеки включает новый выпуск и все его пункты.
